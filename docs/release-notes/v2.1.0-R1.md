# Stack-chan Community 2.1.0-R1

Release impact is minor. This starts the 2.1.0 mod series from the tested R15
checkpoint and Stack-chan v2.1.0. [Upstream release](https://github.com/stack-chan/stack-chan/releases/tag/v2.1.0).

- Keep both integrated conversation modes, the LIVE control, saved Settings
  over Wi-Fi/BLE and application-only updates on M5StackChan CoreS3.
- Use Moddable 10.1.0, including the TLS 1.2 fix and the SDK HTTP header buffer
  fix. Keep the upstream WebRTC lease, lazy HTTPS Worker and awaited cleanup,
  with the fork's cancellable search requests.
- Keep R14 SPI waits and the R15 camera release and reopen behavior. Include
  upstream display batching and the optional Avatar DSL tools.

## Build and scheduling fixes

The generated CoreS3 host entry point pins the realtime XS task to core 0.
The entry point lives in the generated build project. The main file is refreshed
on every build because the SDK Make rule can otherwise replace the pinned copy.
A C/GNUmake regression covers repeated builds and restoration of the standard
entry point for other builds. The realtime XS stack now has 1,024 slots after
a repeated Mini-session startup overflow with 768 slots.

CoreS3 build profiles hash the included application and board manifests and the
SDK identity. A profile change clears the target bytecode, native objects,
SDK objects and application output before dependency preparation. The profile
is committed after a successful build. A failed build invalidates the previous
fingerprint, including when the caller returns to the earlier manifest.
Both firmware wrappers and the release-bundle path use this mechanism.
The regression remaps a module alias to an older source file and checks that
unrelated target output is retained.

The final scheduling order is capture DSP at priority 8, HTTPS at 7 and normal
XS work at 6. Capture and HTTPS use core 0. Codec/RTP placement and the elevated
UI windows are retained. A priority-6 HTTPS request during Mini On resolved DNS
but sent zero HTTP body bytes before failing. Its worker accumulated 1.686 s
of CPU runtime over 17.597 s. Raising HTTPS to 7 with AEC still at 7 completed
search and reported 64 input FIFO overruns, so that combination was rejected.

With AEC at 8 and HTTPS at 7, B35 completed Mini On and Off searches with
HTTP 200, cited sources and zero input FIFO overruns. Each case exercised the
drawer after the device-side search request started. Native worker snapshots
confirmed priority 7 and core-0 affinity. Mini On search took 23.842 s and Off
11.205 s, including remote execution and network delivery. Local stops took
2.603 s and 2.250 s, with successful remote hangups.

## CoreS3 performance comparison

The baseline is [2.0.1-r15](./v2.0.1-r15.md) with Moddable 10.0.2. Both
instrumented builds use ESP-IDF 6.1 and the same connected M5StackChan CoreS3.
The display workload changes the mouth and opens and closes the drawer in
five 40-step runs. The camera workload captures 160 × 120 RGB565 frames.
Provider measurements use synthetic microphone input and the real WebRTC API.
The saved Pitch setting is +3 semitones on both builds. Probe sessions use
Marin and a 3,600-second standby threshold in RAM. The final B36 probe
uses a 1,024-slot XS stack. Its real-API cases run with volume 0 after the
user requested nighttime muting. Audio decoding, Pitch, I2S, capture and On-mode
AEC remain enabled. The earlier R15 API run used the previous saved volume.

The matched short series completed five measured display runs and 50 camera
cycles on each image. Display values below are medians. Idle memory was sampled
once after boot.

The measured XS/SPI task sum fell by 4.127 percentage points of one core.
The XS task ran on core 0 in both R15 and the final R1 probe B36. These
measurements describe this workload. Camera-stop median increased by 1.568 ms.
Whole-device CPU utilization, acoustic quality and end-to-end conversation
speed remain unverified.

On both builds, the camera tasks stopped while the preview bitmap remained
visible. Each of the 50 capture cycles returned a 38,400-byte RGB565 frame,
released both tasks and returned PSRAM to its idle level. Two concurrent

### Extended run and poll watchdog

The first extended run, B19, ended its Live On case at 384.049 seconds with
`event_loop_watchdog`. Its first 37 capture windows had zero input FIFO
overruns and its six repeated playback checks passed before the stop.

The native watchdog subtracted an atomic poll timestamp from a clock read in
the same expression. A concurrent XS poll could publish a newer timestamp after
the older clock was sampled, underflowing the unsigned age. R1 snapshots the
heartbeat before sampling the clock. The deterministic native regression
reproduces the false timeout with the previous ordering, passes with the fix,
and checks real timeout detection and tick-counter wrap. B20 repeated the
device watchdog failure at 100.455 seconds with this fix present. Its trace
omits the two tick reads, so the heartbeat fix alone did not resolve the
extended-run failure. The later scheduling and stack changes were present
in the passing final B36 run.

The final B36 run completed all four cases with the corrected watchdog,
core-0 XS, 1,024-slot stack and capture/HTTPS priorities 8/7. It completed
360 capture windows, 56 repeated playback checks and 62 drawer exercises.
Every window and drawer exercise reported zero input FIFO overruns. The
collector reported no provider failures, close diagnostics or fatal runtime
errors and reached its explicit completion marker.

### Full-duplex control fix and rejected variants

A focused Live On measurement found that `live_peer` accumulated no CPU
runtime between the 5.243-second and 20-second observations. I2S, capture,
encoding, decoding and UI tasks continued accumulating runtime. The public
transport statistics remained at the control task's earlier snapshot, so those
frozen values do not establish that the native microphone stopped.

R1 now schedules Live control at priority 18, matching Mini and peer receive,
below I2S at 20 and encoder/sender at 19. The first focused comparison reached
250 ms of playback in 1.581 s, forwarded 201,280 samples across 12.603 s,
reported zero input FIFO overruns and stopped locally in 1.720 s. The prior
priority-10 case failed its 20-second playback check and took 6.703 s to stop.
These are individual real-API runs. Network and remote generation latencies
are part of their elapsed times.

Three additional scheduling variants were rejected after measuring input loss.
Moving the decoder to core 0 reported eight input FIFO overruns in its first
10.090-second window. Also raising AEC to priority 15 reported 59 overruns
in 10.050 seconds. Pinning the host UI to core 0 with AEC at priority 6 reported 65 overruns
in 10.018 seconds.

Detailed probe records are buffered with a 132-record per-case limit until
audio has stopped. A small marker confirms progress every thirty seconds.
Large records are sent in paced 128-character chunks after one additional
baseline attempt lost part of a USB record. The extended test repeats real API
playback every minute and can check the existing speech fixture and both
search paths. The speech fixture is injected digitally before AEC. The passing R14 fixture
is 71,032 bytes, SHA-256
`46b48a29d7f14a07ca8dc7f7bb1c406fd124ba6cf7e582fd8b6b6a2c709ff41d`.
It was recovered from the existing generated English greeting WAV with
`volume=2,alimiter=limit=0.9:level=0` at 16 kHz mono PCM16. An earlier
cheer-up asset fixture passed Mini input but did not establish Live input
acceptance. Live then passed with the recorded fixture. Search checks use
a fresh session after the speech check so an answering turn cannot collide
with the diagnostic forced search.

## CoreS3 flash and preference validation

The app-only writes started at `0x10000` after checking the live partition
table and application bounds. Standard writes repeatedly failed MD5
verification. Uncompressed 4 KiB transfers with a 4 ms inter-block pause
restored the R15 app and allowed subsequent writes. An independent verification
matched the application before resetting the device. The cause of the original
transfer failure is unknown.

An incremental diagnostic build picked up the production preference module.
It rewrote the TTS volume key with the same value before failing its guard
check. Read-back found 35 different bytes in the NVS partition. The ESP-IDF
NVS parser verified identical payloads for all 29 active entries, with the
volume record moved within its original page. The other protected data matched
the private pre-test backup. Later probes require the guard before attempting
the test write, and their clean builds were checked for the guarded module and
the expected partition layout before flashing.

A later read-back found refreshed ESP-IDF PHY calibration under `phy.cal_data`.
The installed ESP-IDF 6.1 source owns this key in
`components/esp_phy/src/phy_init.c`. Its refresh trigger is unknown.
The user then requested volume 0.1 and subsequently complete muting. The
saved `tts.volume` is now 0, independently read back from NVS.

After installing the final production app at `0x10000`, the final audit
matched all 25 remaining active NVS entries, excluding only the authorized
volume key and PHY calibration. All protected bytes outside NVS matched
the original backup, including the bootloader, partition table, `xs` and
storage. The app MD5 matched the canonical release image after an independent
reconnect. The 45-second normal-firmware smoke observed network readiness,
application context creation and `app behaviors ready`, with no fatal runtime
markers. A subsequent protected-partition read was byte-identical to the
pre-smoke read, and the normal firmware was restarted.

The first normal-boot collector exited on a nonblocking USB read returning
`EAGAIN` during reset. Its retry handling was corrected before the successful
45-second run. This was a collector failure. The raw device backups and
logs remain private outside Git.

The validated application is 8,558,992 bytes with SHA-256
`b2335bcc4eecf24d88cb3da3ec569302dd96cbf1edcd8f5c3adf99d310e3eddb`.
The matching 16,777,216-byte full image has SHA-256
`65335a9c2193a3ed42d35c88fe3d72f1c1c69c2e4eca44584b637da87fde5a2c`.
The full image is assembled from the same bootloader, partition table and
application, with every remaining byte set to `0xFF`.

The initial R1 comparison exposed a build configuration problem. The Moddable
10.1.0 board manifest overrode `SDKCONFIGPATH`, leaving 40 MHz PSRAM and DIO
flash in the generated SDK configuration. The firmware wrapper now applies the
CoreS3 overlay after the board manifest. Both final generated configurations
select QIO flash, 80 MHz PSRAM, a 240 MHz CPU and size optimization (`-Os`).
The 40 MHz diagnostic is excluded from the final paired measurements.

The probe builds from `firmware/` in the configured SDK environment through
`npm run build -- --mode=release --manifest host/app/manifest_openai_camera_probe.test.json`.
B36 uses a private manifest overlay setting `cameraProbeSeconds=900`,
`cameraProbeSpeech=true`, `cameraProbeSearch=true`,
`cameraProbeVoiceUI=true` and `cameraProbeVolume=0`. The private fixture
resource contains the PCM identified above. The collector is armed before
the verified application reset, with a 4,500-second total bound, 45-second
startup bound and 55-second progress bound. It uses the tracked
`firmware/scripts/capture-r14-complete.py` collector with the
`camera-probe` marker and camera events enabled. The flash adapter and raw
logs remain private because they contain device metadata.
