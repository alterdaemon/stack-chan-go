# Stack-chan Community 2.1.0-R1

Release impact is minor. This starts the 2.1.0 mod series from the tested R15
checkpoint and Stack-chan v2.1.0. [Upstream release](https://github.com/stack-chan/stack-chan/releases/tag/v2.1.0).

- Keep both integrated conversation modes, the LIVE control, saved Settings
  over Wi-Fi/BLE and application-only updates on M5StackChan CoreS3.
- Use Moddable 10.1.0, including the TLS 1.2 fix and the SDK HTTP header buffer
  fix. Keep the upstream WebRTC lease, lazy HTTPS Worker and awaited cleanup,
  with the fork's cancellable search requests.
- Keep R14 SPI waits and the R15 camera release and reopen behavior. Include
  upstream display batching and the optional Avatar DSL tools.

## Validation

- Firmware: 663 Node/native tests with serial test execution, nine packaging
  tests, 11 RFID tests, 76 architecture checks and three board provider tests.
  Lint, formatting, manifest preflight for six targets and
  `npm run check:release -- v2.1.0-R1` passed.
- Linux XS: integrated LIVE control and shutdown, Settings view, native
  transport and Wi-Fi Settings HTTP server passed using the headless screen
  runner.
- Avatar DSL: 870 native cases, 73 matching native/reference frames and nine
  cached redraws passed. The native translation unit also compiled for all four
  ESP32-S3 display rotations with the generated board flags.
- Web: 240 legacy tests passed and two optional tests were skipped. All 99
  React tests, the editor artifact check and the production Web build passed.
- `npm run build -- --mode=release` produced the 9,241,168-byte application
  and 16 MiB full image from the same M5StackChan CoreS3 build. The app matches
  the bytes at `0x10000` in the full image. The bootloader and partition table
  match the build outputs, and the connected device's table matches the
  supported layout. The `build:release:m5stack_cores3` and
  `build:release:m5stackchan_cores3` commands built and validated both CoreS3
  bundle targets.

The release build ran in a short-path worktree. The Moddable linker command
exceeded the shell argument limit at the original checkout path.

## CoreS3 performance comparison

The baseline is [2.0.1-r15](./v2.0.1-r15.md) with Moddable 10.0.2. Both
instrumented builds use ESP-IDF 6.1 and the same connected M5StackChan CoreS3.
The display workload changes the mouth and opens and closes the drawer in
five 40-step runs. The camera workload captures 160 × 120 RGB565 frames.
Provider measurements use synthetic microphone input and the real WebRTC API.

The first run completed the display workload on both builds. Display values
below are medians of the five runs, with free memory sampled once after boot.

| Metric | 2.0.1-r15 | 2.1.0-R1 diagnostic |
| --- | ---: | ---: |
| SPI submissions per display run | 1,857 | 216 |
| Bytes submitted to SPI | 785,816 | 865,180 |
| Longest measured frame duration per run | 24.26 ms | 22.92 ms |
| XS plus SPI runtime, as a share of one core | 25.67% | 26.84% |
| Free PSRAM at idle | 6,765,996 B | 7,281,072 B |
| Free internal RAM at idle | 143,171 B | 147,711 B |
| Largest free internal RAM block at idle | 94,208 B | 94,208 B |

The new build made 88.4% fewer SPI submissions and sent 10.1% more bytes.
The XS task ran on core 1 in the baseline and core 0 in the new build. This
series cannot establish a change in CPU efficiency.

On R15, all eight camera cycles returned a frame and released both camera
tasks. Median start-to-frame time was 377.8 ms and median stop time was
49.2 ms. Each stop recovered 115,436 B of PSRAM. The two concurrent one-shot
captures returned readable copies after teardown. Both provider modes connected
after the camera test with voice interruption on and off. Capture advanced
through four 12 s sessions with zero reported FIFO overruns or underruns.
One session reported an unconfirmed remote hangup.

The first R1 diagnostic rendered the preview bitmap. Its fixed-delay check
sampled camera tasks before the 120 ms post-render stop delay had expired.
The updated probe observes task creation and exit, repeats capture 50 times
and requests real API playback with synthetic microphone input.

## Device validation pending

The two initial diagnostic images passed write verification and started on the
device. Subsequent application writes failed flash MD5 verification, including
the R1 production image and the previously validated R15 image. The failure
reproduced with esptool 5.6.0 and 4.9.0, with compressed and uncompressed
transfers, with the ESP32-S3 ROM loader, and after resetting the flash chip's
volatile state. An application read-back after the second failed R1 write
still matched the previous diagnostic image in 2,256 of 2,256 complete 4 KiB
sectors. The cause remains unknown.

Every write was confined to the application at `0x10000`. All 458,752 bytes
outside that partition matched the pre-test backup, including the bootloader,
partition table, NVS, `xs` and storage. The production boot and the R15
restoration remain unverified. The release tag is pending the hardware check.

The revised diagnostic built for both versions. A matched second run, the
50-cycle camera check, real API playback comparison, sustained session test
and acoustic check remain pending.

The revised probe builds from `firmware/` in the configured SDK environment.
The collector runs from the repository root after a verified app-only write.

```sh
npm run build -- --mode=release --manifest host/app/manifest_openai_camera_probe.test.json
python3 firmware/scripts/capture-r14-complete.py --port <port> --startup 45 --seconds 300 --marker camera-probe --camera-events
```
