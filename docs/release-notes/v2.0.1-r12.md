# stackchan-community-mod 2.0.1-r12

Release impact: patch.

R11 firmware `923efc8f` / `v2.0.1-r11` and both R11 BINs remain the rollback
baseline. The user declined device backups. All esptool writes in this session
were validated application-only writes at `0x10000`. No partition contents were
backed up after that instruction; probe overrides did not call Preference.set.

## Changes

Full-duplex LIVE enables a native 20 ms UI scheduling period. XS gets an 8 ms
priority-20 window, extended to 12 ms while touching the interface. A native
250 ms touch deadline handles a missed release even when JS is delayed. I2S
retains priority 20 and remains eligible alongside XS. The existing `spiLoop`
display dependency gets priority 21; it normally blocks waiting for DMA. Idle
windows leave 12 ms at the original XS priority; touch windows leave 8 ms.
Unused windows do not create UI work. No audio task changes core, priority,
frame processing, AEC configuration or FIFO capacity. Closing retains this
policy until native cleanup completes; then both original priorities and the
timer allocation are restored. Interruption Off does not enable the policy.

The dependency matters: the installed Moddable SDK's
`modules/pins/spi/esp32/modSPI.c` creates `spiLoop` at priority 10, while
`modSPIFlush` busy-yields until it drains pending display transactions.
Boosting XS alone can therefore prevent its display dependency from running.
Raising SPI alone did not resolve the measured UI problem either.

The mouth meter reads the samples written to I2S, after existing DSP and volume,
without waiting for capture/AEC statistics. It reuses the existing PCM loop and
100 ms mouth timer, with no new audio traversal or allocation per frame.

Graceful close silences microphone/output while keeping media clocks alive
until transport cleanup. Late provider errors no longer replace a requested
standby result. After successful local cleanup, a missing remote close
acknowledgment yields STANDBY with a diagnostic and retained RAM history.
Cleanup failures remain errors. Explicit STOP still clears history. The existing
auto-disconnect deadline, delegated-backend tracking, bounded history and saved
Voice/Pitch/Style are unchanged. STANDBY does not assert remote finalization
when `session.closed` was not received.

Protocol: [OpenAI graceful close](https://developers.openai.com/api/docs/guides/live-conversations).
Timer lifecycle: [Espressif ESP Timer](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/esp_timer.html).

## Autonomous device validation, 2026-11-10

The real CoreS3 used Wi-Fi, its saved API credential and the live OpenAI API.
Probe settings and measurements remained in bounded RAM. Saved Pitch was kept
constant throughout the final series; it was not an experimental variable.
The probe installed the real integrated MOD and exercised drawer rendering,
simulated touch scheduling, native I2S, AEC, Opus and networking. The greeting
counted to 15. A known existing voice clip was injected before AEC two seconds
after actual speaker playback began, independently of JS progress.

The control used original main/SPI priorities 6/10. It delivered the voice clip
to the model, automatically reached STANDBY and retained 6 transcript fragments.
Then four configurations were compared in RAM within one connection:

| Main / SPI priority | Idle / touch window per 20 ms | Max UI heartbeat gap | Max screen callback | Max I2S write gap |
| --- | --- | --- | --- | --- |
| 20 / 21 | 2 / 6 ms | 1088.311 ms | 523.407 ms | 11.752 ms |
| 20 / 21 | 4 / 8 ms | 342.105 ms | 182.558 ms | 11.798 ms |
| **20 / 21** | **8 / 12 ms** | **159.432 ms** | **83.373 ms** | **11.908 ms** |
| 21 / 22 | 4 / 8 ms | 523.638 ms | 123.376 ms | 18.299 ms |

The original-priority control measured a 2855.095 ms UI gap and a
1916.462 ms screen callback, with a 10.544 ms I2S write gap.
These are maximum observations in these scenarios, not guaranteed latency
limits or exhaustive optimization results. The configurations ran sequentially;
network/model workload was not identical across their windows.

A new session with the selected 20/21, 8/12 ms policy verified:

- 6 history fragments supplied when resuming; 6 retained after automatic STANDBY.
- Input transcript received after the known clip entered the microphone path
  during playback; all 41,796 injected samples entered the pipeline.
- 0 reported capture FIFO overruns; max I2S write/read gaps 11.215/11.427 ms.
- Max connected UI gap 427.538 ms and screen callback 100.417 ms across the
  longer conversation, including input and API events. Remaining latency spikes
  are therefore not claimed eliminated.
- A missing remote close acknowledgment produced `close_timeout` diagnostics,
  followed by local cleanup and STANDBY with history, rather than ERROR.
  The existing 15-second remote-close grace period was not shortened in firmware.

This verifies the digital interruption path and device scheduling progress.
It is not a physical acoustic-microphone test, a visual camera assessment or a
recording of speaker quality. DMA service gaps alone do not prove acoustic
quality, and underrun counters do not distinguish intentional silence from
missing network PCM.

Earlier instrumented attempts were rejected rather than published. Main-only
priority 21 reached a 9298.153 ms UI gap; a later main-16/SPI-17 attempt reached
4236.980 ms. Serial report calls themselves took up to 961.709 ms under load.
The final series buffers per-profile results in RAM and prints them after
stopping audio, with only small progress events during measurement. A quieter
English fixture did not produce an input transcript; the final control and
selected-policy verification used the identical previously passing existing
clip. Those failed fixture runs do not establish an acoustic regression.

## Faster repeatable testing

One probe build/flash runs a voice-input control, four RAM priority/window
profiles, and the selected-policy automatic-standby/resume/input verification.
The serial collector checks startup within 30 seconds and rejects missing
results or failed standby/history/input checks. Control stops as soon as input
is confirmed; guards are 25/35/60 seconds for control/sweep/verification, with
an overall capture bound of 180 seconds. These are guards, not fixed sleeps.
The final physical run above preceded the early-control-stop optimization.

Normal esptool RAM-stub flashing at baud 921600 reduced application writing
from approximately 73 seconds with `--no-stub` to 25.0–25.2 seconds, excluding
hash verification/restart. It still writes only the application at `0x10000`.
[Espressif RAM-stub documentation](https://docs.espressif.com/projects/esptool/en/latest/esp32s3/esptool/flasher-stub.html).

Probe reproduction, from the repository root in the existing toolchain setup:

```sh
ffmpeg -v error -y -stream_loop 2 -i firmware/mods/examples/cheerup_ble_lite/assets/04-wonderful.wav -af 'volume=4,alimiter=limit=0.9:level=0' -ar 16000 -ac 1 -f s16le firmware/dist/probe-input.pcm
STACKCHAN_REALTIME_WEBRTC=1 STACKCHAN_TOOLCHAINS=<existing-toolchains> bash build-gpt-live.sh --mode=release --manifest host/app/manifest_openai_live_probe.json
python3 firmware/scripts/capture-live-probe.py
```

Validate the application/table against `gpt-live-layout.json` before the
application-only esptool write. The initially read device partition table
matched that layout, and no partition-table write was performed. ROM MD5 also
confirmed that the originally installed application matched the R11 BIN.
Only MD5 digests, not contents, were retained for protected partitions.
