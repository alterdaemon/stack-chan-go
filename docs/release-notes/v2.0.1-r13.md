# stackchan-community-mod 2.0.1-r13

Release impact: minor.

## Changes

OpenAI settings now offer **GPT-Live 1** (`gpt-live-1`) and
**GPT-Realtime 2.1 Mini** (`gpt-realtime-2.1-mini`). GPT-Live remains the
default. Mode and voice changes take effect on the next LIVE start. Wi-Fi
and BLE share the form and preference validation. Voice choices are stored
independently; existing Live voice/pitch/style and user preferences are retained.

Mini establishes a direct WebRTC call and uses server VAD with automatic
responses. Interruption follows the saved opt-in setting. Mini does not run
the GPT-Live auto-disconnect timer or import its standby transcript tail.
Explicit STOP closes the session; API/network failures require manual restart.
The shared native WebRTC/Opus/I2S/AEC/pitch pipeline and R12 follow-up's 4/8 ms
UI scheduling policy are retained. This is not a claim of verified acoustic quality.

Mini keeps voice interruption available through the existing opt-in setting.
Only Mini's AEC processing priority changes from 6 to 7, above normal UI priority;
capture returns to its existing priority after each frame. GPT-Live keeps AEC
priority 6. I2S, Opus, RTP, AEC parameters, buffers and UI windows are unchanged.
Mini control messages run at priority 18 instead of Live's 10. The shared HTTPS
worker runs on core 0 at priority 6, below Mini AEC (7), to leave I2S, encoding
and RTP on core 1. No new task is created. Mini On uses
server VAD threshold 0.3; Off uses 0.5. Startup verifies the echoed threshold,
automatic response and interruption configuration before reporting connected.
The prompt amendment below also verifies the echoed instructions before opening
microphone input.

Realtime function `search_web` calls Responses directly from the device,
using the existing backend model and thinking effort. Only a bounded query
is sent; the result contains a bounded answer and source URLs. One search
request can run at a time. HTTPS and search-result parsing run in the existing worker, with a 45-second
deadline and 128 KiB response bound. STOP, interruption during pending search,
and tool timeout cancel work and suppress late results. No external server,
new audio queue, local VAD or persistent conversation storage is introduced.

Official protocol references:

- [Realtime Mini model](https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini).
- [WebRTC call creation](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/create).
- [Realtime VAD](https://developers.openai.com/api/docs/guides/realtime-vad).
- [Function calls and conversation lifecycle](https://developers.openai.com/api/docs/guides/realtime-conversations).
- [Responses web search](https://developers.openai.com/api/docs/guides/tools-web-search).

### System prompt amendment

The user requested an amendment of R13, including its commit, tag and two images.
This is not a new firmware revision. No saved preferences are migrated or written.

Two issues were distinguished:

- The old Mini startup checked VAD but accepted different echoed instructions.
  A regression reproduced that incorrect connected state. Startup now checks
  exact instruction equality, reapplies instructions and VAD in the existing
  single setup update when needed, and rejects an incorrect acknowledgment.
  Local microphone input stays muted until configuration is acknowledged.
- Exact receipt did not establish personality compliance. With all 818 saved
  characters confirmed, Mini repeatedly gave friendly greetings while Live
  used the requested sarcasm. This also occurred with text output; neutral
  replies were final answers, not just commentary. The model-side reason is
  unknown. Extra system/user context, per-response copies, style reminders,
  seeded examples and higher reasoning effort did not establish the desired
  greeting behavior and are not included in production.

The selected Mini instructions frame the task as writing and speaking the next
line of dialogue for the assistant specified in the saved prompt. The complete
saved text follows unchanged, including its examples. The framing explicitly
applies the configured character to greetings while requiring accurate answers.
This is assembled once per session in RAM. It adds 317 characters for this prompt,
no model calls, timers, audio processing or per-turn client requests. GPT-Live's
instructions, saved settings, VAD, tools and interruption priorities are unchanged.

The [Realtime reference](https://developers.openai.com/api/reference/resources/realtime/client-events)
defines session and response instructions as behavior guidance, without a compliance
guarantee. The [prompting guide](https://developers.openai.com/api/docs/guides/voice-prompting)
recommends clear task/personality sections. Neither source establishes a special
Mini-only personality field or documents the cause of the observed difference.
The task framing was selected from device/API results, not a claimed API requirement.
