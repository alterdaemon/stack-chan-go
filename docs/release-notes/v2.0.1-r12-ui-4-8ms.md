## Audio scheduling

The user reports unintelligible agent speech and unreliable interruption on
the original 8/12 ms build, and has not installed the intermediate 6/10 ms
build. At the user's request, shorten both UI boost windows by another 2 ms:

| UI scheduling interval per 20 ms | Stable reference | Superseded candidate | This build |
| --- | --- | --- | --- |
| Elevated priority without touch | 8 ms | 6 ms | 4 ms |
| Base priority without touch | 12 ms | 14 ms | 16 ms |
| Elevated priority during touch | 12 ms | 10 ms | 8 ms |
| Base priority during touch | 8 ms | 10 ms | 12 ms |

Longer base-priority intervals give codecs/RTP more opportunity to run; they
do not reserve CPU time or prove intelligible speech. Priorities, affinities,
SPI handling, touch expiration, AEC/effect processing and the connected-session
microphone gates are unchanged. The UI policy applies only with Interruption
On. Interruption sensitivity and perceived reactivity remain unverified; no
local VAD, forced interruption or AEC bypass was added.

## LIVE start and stop

Source inspection found a 15-second remote-close grace timer and a local
quiesce request applied only when the peer task next updated audio. The LIVE
button rejects another start while the current session is closing.

- Call local quiesce when close starts, even during startup before protocol
  close can be sent. The existing native hook sets the active audio object's
  atomic quiesce flag under its lifetime lock, without waiting for the peer
  task. I2S/capture/encoding continue with silent media for graceful close;
  resource release still happens through the existing teardown sequence.
- Shorten the remote-close grace timer from 15 to 3 seconds. This is a timeout
  for acknowledgment, not a guarantee that all SDK cleanup finishes in 3 s.
- After successful local cleanup, explicit STOP returns to idle even if remote
  finalization is unconfirmed; it retains a diagnostic and clears RAM history.
  Automatic STANDBY retains history as before. Earlier failures and actual
  cleanup failures still yield ERROR.
- If STOP arrives during native audio initialization, skip starting WebRTC
  once audio initialization returns and proceed directly to cleanup.

A fresh start still needs native media setup, HTTPS session creation and
WebRTC negotiation. There is no fixed startup sleep to remove. No cold-start
speedup has been measured or claimed. Shorter shutdown can reduce the wait
before restarting, but a new session is never started over unreleased audio.

OpenAI Docs permits an application-defined finalization timeout, while requiring
`session.closed` for confirmed finalization. Missing confirmation remains
explicitly recorded; media clocks are kept alive until cleanup.
[Official graceful-close guidance](https://developers.openai.com/api/docs/guides/live-conversations#usage-and-graceful-close).
