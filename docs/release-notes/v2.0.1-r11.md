# stackchan-community-mod 2.0.1-r11

Release impact: minor.

The final R11 amendment uses one standby timer. It starts when LIVE connects,
with a default of 60 seconds. Only a nonblank assistant output transcript renews
the full interval. User transcripts, microphone noise, audio/PCM counters and
usage heartbeats cannot renew it. There is no periodic inactivity poll or local
VAD; its detector, allocation and native capture work have been removed.

A pending Responses request to the delegated model pauses the timer, including
quiet reasoning/search. This means an actual `session.delegation.created` or
nested Responses lifecycle start, not merely an open connection. Completion,
failure, cancellation or an incomplete response removes the corresponding
request. When the last pending request ends, the full configured interval starts.
Overlapping request IDs remain bounded and correlated through delegation/response
IDs. Unrelated backend events do not renew a running timer.

OpenAI Settings now contains **Auto disconnect (seconds)**, default **60**,
accepting whole seconds from **1 to 3600**. Wi-Fi and Bluetooth share the same
field, validation and `openailive.standbySeconds` preference. Older firmware must
advertise the field before the web form enables it. Saved changes apply to the
next LIVE start, including resume. Invalid stored values use firmware defaults.

The timeout rule is independent of Pitch and Voice interruption On/Off. Its
speech signal is the assistant's nonblank output transcript, not a sample-level
measurement of when sound reaches the listener. Thus the deadline is measured
from transcript delivery; it is not an acoustic end-of-speech timestamp.

At expiry, the existing close path sends `session.close` and stops local audio,
then waits for `session.closed` and releases native resources. A 15-second
finalization timeout still releases local resources and reports ERROR rather
than claiming successful remote finalization. STANDBY appears on the existing
LIVE button after cleanup. There is no automatic microphone wakeup.

Native cleanup closes WebRTC, capture, playback, I2S, AEC and Pitch. Host audio
ownership and the low-latency radio lease are returned after native shutdown;
the amplifier returns to 24 kHz. Manual LIVE resumes with at most 6
consecutive-speaker fragments / 2048 characters in RAM via `session.input`.
Explicit STOP, an error or restart clears this tail. No transcript is stored in
NVS. Saved Voice, Pitch, Style, interruption and backend options are reread.

The user confirmed that the preceding R11 (`14753361`, app `0c688248…`)
keeps interruption working and removes UI lag, but playback now stutters.
That build lowered priority around AEC while AEC and I2S still ran in the
same task. Consequently, delayed AEC also delayed the next I2S write/read.
This is an observed dependency in the code; physical CPU load and timing
have not been measured here.

Earlier attempts were reviewed before implementation:

| Source snapshot | Mechanism | Evidence/result |
| --- | --- | --- |
| R10 through `fda883d3` | Priority-3 AEC worker, four-slot ring with three usable slots; worker core 0 then 1; capture core 1 then back to 0; silent-reference bypass later removed | User-tested R11 still lost interruption. Source permits rejecting new frames when full. A compiled historical-worker fixture rejects the fourth 32 ms frame while the first is held. The acoustic root cause of those failures was not measured. |
| `2bd6185c` | Synchronous AEC in the priority-20 I2S task | User confirmed interruption, with severe UI lag. |
| `14753361` | Same task, priority 6 only during AEC | User confirmed responsive UI and interruption, with playback stuttering. The new concurrent fixture detects that DSP still runs in the speaker task. |

This amendment keeps the existing tasks and their affinities: I2S/Pitch at
priority 20 on core 1 with On; capture (`AUD_SRC`) on core 0; Off's audio on
core 0. It moves AEC processing into the existing capture reader. I2S copies
complete, paired planar microphone/reference frames into its existing input
FIFO and continues servicing the speaker without waiting for DSP.

`sourceRead` processes each queued frame sequentially using the unchanged AEC
instance, FD mode and NLP parameters. Only DSP runs at priority 6, matching UI;
the capture priority is restored immediately afterwards. Processed tails are
retained across differently sized encoder reads, then forwarded through the
existing mute/gating/transform path. There is no local VAD, silence bypass,
forced stop, new AEC worker, additional queue or per-frame allocation.

With On, the existing FIFO holds two channels instead of clean mono: 12,800
bytes instead of 6,400, retaining the same nominal 200 ms capacity. As before,
a full input FIFO counts an overrun and rejects a whole frame; sustained
capture overload remains a limit, not a guaranteed lossless operating mode.
The concurrent delay regression explicitly requires zero overruns and verifies
every sample, rather than allowing drops as the old worker fixture did.
Two additional per-session AEC sample planes separate producer/consumer
workspace (2,048 bytes at the current 512-sample chunk). On's capture task gets
an 8 KiB internal-RAM stack, matching the former DSP stack budget. Off retains
its previous FIFO, sample allocation, stack policy and priorities.

UI priority/affinity and the screen scheduler are unchanged in both modes.
Native cleanup already stops capture before destroying AEC or freeing the
shared allocation; no task or timer is added. Standby/history, preferences,
protocol, Voice/Pitch/Style and Pitch DSP remain unchanged. R11 is amended at
the user's explicit request.

Scheduling source: Espressif's [FreeRTOS scheduler](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/freertos_idf.html#smp-scheduler).
The installed esp_capture 1.0.4 source (`gmf_audio_src.c`) calls `read_frame`
from the existing `AUD_SRC` task in its default asynchronous-read mode. This
application does not enable its optional synchronous-source-read mode.

Protocol sources: OpenAI's [session lifecycle and startup history](https://developers.openai.com/api/docs/guides/live-conversations)
and [Live event reference](https://developers.openai.com/api/reference/resources/live/primary-websocket).

Validation for this amendment (2026-11-10):

- `npm run test:unit`: 594 passed, followed by 9 packaging tests.
- Native regression compiles the actual `liveAudio.c` with ASan/UBSan and
  concurrent I2S/capture threads. Every Pitch -6 through +6 is exercised with
  On/Off, plus explicit mute. The I2S task advances 100 ms of virtual audio
  while AEC is held, with no input overrun. Sample sequences and paired
  reference are checked through repeated FIFO wraps and varying encoder frame
  sizes, including the cached AEC tail. It also checks priorities, mute,
  timestamps and stop/restart isolation. The expanded run covers 3.2 seconds
  of virtual input per case; the targeted native test passed separately after
  extending its duration. These are hardware/DSP/RTOS test doubles, not a
  physical or acoustic performance measurement.
- Negative controls compile historical production C: the preceding R11 fails
  because AEC executes in the I2S task; the former `fda883d3` worker rejects
  the fourth 32 ms frame while its first frame is held. Both failure conditions
  are covered by the new concurrent test.
- Firmware lint and formatting passed; lint retains its existing informational
  connectivity-test diagnostic.
- `npm run check:release -- v2.0.1-r11` passed.
- CoreS3 release build, embedded web build and automatic packaging passed:
  `STACKCHAN_TOOLCHAINS=<existing toolchains> bash build-gpt-live.sh --mode=release`.
- ELF audit confirms `audioTask` calls neither AEC nor priority-change APIs;
  `sourceRead` contains the AEC call and its priority guard. No old AEC worker
  or UI-affinity wrapper is linked.
- Image audit: application 8,505,072 bytes; full flash 16,777,216 bytes. The
  app matches both build copies and its range at `0x10000` in the full image.
  Bootloader/table match the same build and validated offsets; every other
  byte is `0xFF`. Both R11 images were replaced; earlier revisions retained.
  Application SHA-256:
  `445038b34240d94f2b957e6ce96b3b06af08dcfb73fb8778bdc14f5e486b7c9d`.
- Source audit confirms standby/history, preferences, protocol, Pitch DSP and
  UI/platform implementation remain byte-identical to the preceding build.
  Only native audio/capture code, regressions and documentation changed.
  Agent guidance now requires reviewing previous attempts and testing progress
  plus data continuity for concurrency changes.

Physical interruption, UI responsiveness, playback quality and SRAM headroom
still require the user's CoreS3 test. Source and fixture results do not establish
that all three device behaviors are now correct.

Previous R11 validation covered the one-shot standby timer, backend pause/resume,
RAM history, native cleanup and the OpenAI setting through unit tests and XS
integration. It also covered all 26 Pitch/Interruption option combinations with
media statistics unavailable. These do not verify ESP-SR acoustic cancellation
or physical UI latency. No physical CoreS3 or live API tests can be run in this
environment; the user performs device installation/testing.
